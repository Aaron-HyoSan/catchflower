# A. 와이어프레임 문구 · 버튼 스펙

> 캐치플라워 앱에 들어가는 **모든 화면 문구와 버튼 텍스트**의 확정안.
> 와이어프레임(`와이어프레임/*.svg`)에 실제로 그려진 문구와 1:1 일치한다.
> 디자인 작업 시 이 문서의 문구를 그대로 사용하고, 임의로 줄이거나 바꾸지 않는다.

---

## 0. 문구 작성 원칙

주 타깃이 **40~50대 여성**이라는 점이 모든 문구 판단의 기준이다.

| 원칙 | 하지 않는다 | 한다 |
|---|---|---|
| 게임 용어를 앞세우지 않는다 | 퀘스트, 미션, 랭킹업, 컬렉션 | 꽃 모으기, 순위, 도감 |
| 시스템 어투를 쓰지 않는다 | "인식 실패", "처리 중", "오류 발생" | "알 수 없었어요", "보고 있어요" |
| 실패를 사용자 잘못으로 만들지 않는다 | "잘못 촬영하셨습니다" | "다시 한 번 찍어 주시겠어요?" |
| 동작을 지시한다 | "적절한 거리에서 촬영" | "네모 안에 꽉 채워 주세요" |
| 규칙은 이득으로 설명한다 | "시즌 점수 증가 없음" | "사진은 도감에 쌓여요" |
| 외래어는 대중 인지명만 | 컬렉션, 피드, 프로필 편집 | 도감, 기록, 프로필 수정 |
| 숫자는 단위까지 | "37" | "37종", "4회", "47일 남음" |

**어미 통일** — 안내문은 `~어요/~아요` (부드러운 구어), 버튼은 명사형 또는 `~기` (`공유하기`, `다시 찍기`).
경어 `~하십시오`, `~하시겠습니까` 는 쓰지 않는다.

## 1. 버튼 · 텍스트 스타일 정의

디자이너가 컴포넌트로 만들어야 하는 최소 단위.

### 버튼

| 종류 | 용도 | 사양 | 예시 |
|---|---|---|---|
| Primary | 화면의 주 행동, 화면당 1개 | 높이 **56px**, 라운드 완전(28px), 채움, 굵게 15~16pt | `네, 맞아요` `공유하기` |
| Secondary | 대안 행동 | 높이 **54~56px**, 테두리 1.5px, 흰 배경, 굵게 15~16pt | `아니에요, 다시 찍을게요` |
| Ghost | 회피·보조 | 높이 50px, 연한 회색 배경, 중간 굵기 15pt | `나만 보기` `나중에 할게요` |
| Small | 카드 내부 | 높이 32~40px, 12~13.5pt | `길찾기` `추가` `초대하기` |
| Text | 최소 강조 | 굵게 13pt, 밑줄 없음 | `공유하지 않기` `전체 보기` |
| Disabled | 조건 미충족 | 회색 배경 + 회색 글자, 문구를 안내로 교체 | `동네를 선택해 주세요` |

- **최소 터치 영역 44×44px**. 아이콘 단독 버튼도 이 값을 지킨다.
- 아이콘만 있는 버튼은 만들지 않는다. **반드시 텍스트를 병기**한다 (`좋아요 12`).

### 텍스트

| 역할 | 크기 | 굵기 | 용도 |
|---|---|---|---|
| 화면 제목 | 19~21pt | Bold | 헤더 `내 꽃 도감` |
| 축하/질문 대상 | 24~32pt | Bold | `장미`, `연남동 4위` |
| 섹션 제목 | 13.5~14.5pt | Bold | `최근 발견한 꽃` |
| 본문 | 12~13.5pt | Regular | 설명문 |
| 보조 설명 | 10.5~11.5pt | Regular | 회색 부연 |
| 최소 크기 | **10.5pt** | - | 이보다 작게 쓰지 않는다 |

> 노안을 고려해 본문 최소 12pt를 권장한다. 10.5pt는 날짜·개수 등 보조 정보에만 쓴다.

### B-5 하루 중복 안내 (2026-08-05 추가 · iOS 세션)

**왜 추가했나.** B-5(같은 종 + 같은 장소는 하루 1회)는 오너가 확정한 규칙인데
**이 문서에 문구가 없었다.** 규칙은 있고 사용자에게 할 말이 없으면 개발이 막힌다.
0절 원칙(실패를 사용자 잘못으로 만들지 않는다 · 이유와 대안을 같이 준다)에 맞춰 썼다.
**오너 검토 대상이다.**

| 요소 | 문구 |
|---|---|
| 제목 | 오늘 여기서 만난 꽃이에요 |
| 설명 | 같은 자리에서 같은 꽃은 하루에 한 번 기록해요. |
| 설명 2 | 장소를 옮기면 다시 기록할 수 있어요. |
| 버튼 (주) | 도감에서 보기 |
| 버튼 (보조) | 다른 꽃 찍기 |

**"어제는 됐는데 오늘은 안 되는" 상황이 아니라는 걸 분명히 한다** —
막는 게 아니라 **이미 기록됐다**는 뜻이라서 제목을 부정형으로 쓰지 않았다.

### B-3 어뷰징 가드 ① 희귀종 추가 확인 (2026-08-05 추가 · iOS 세션)

**왜 추가했나.** B-3 대응 1번(`희귀종을 낮은 순위에서 고르면 즉시 확정하지 않고
사진을 한 장 더 받는다`)은 오너 확정 규칙인데 **문구가 없어서 구현이 멈춰 있었다.**

**가장 조심해야 하는 문구다.** 실제로 귀한 꽃을 만난 사람이 대다수이고,
어뷰징하는 사람은 소수다. **다수를 의심하는 말투가 되면 안 된다** —
0절 원칙 `실패를 사용자 잘못으로 만들지 않는다`가 여기서 가장 강하게 걸린다.
그래서 "확인이 필요합니다"가 아니라 **"귀한 꽃이라 한 장 더"**로 썼다.
검증이 아니라 **대접**으로 읽히게 한다. **오너 검토 대상이다.**

| 요소 | 문구 |
|---|---|
| 제목 | 귀한 꽃이네요! |
| 설명 | {꽃이름}은 보기 드문 꽃이라 사진을 한 장 더 받아요. |
| 설명 2 | 조금 다른 각도에서 찍어 주시면 좋아요. |
| 버튼 (주) | 한 장 더 찍기 |
| 버튼 (보조) | 다시 고르기 |

`다시 고르기`는 후보 선택(화면 09)으로 돌아간다 — **잘못 골랐을 수 있기 때문이다.**
`나중에`나 `취소`를 두지 않은 이유: 여기서 빠져나가면 등록이 안 된 채로 끝나는데,
그건 사용자가 원한 결과가 아니다.

### 화면 17 지역 랭킹의 빈·실패 상태 (2026-08-08 추가 · AOS 세션)

**왜 추가했나.** 랭킹을 서버에서 받게 하면서 화면 17이 **문구가 없는 상태 네 개**를
갖게 됐다. 2절 17번 표는 "랭킹이 있는 화면"만 적혀 있어서, 없을 때 화면이 텅 빈다.
**오너 검토 대상이다.**

**실측으로 확인한 사실이 이 표의 근거다.** 서버 `region_ranking`은
① 활동 지역을 안 정했을 때와 ② 정했지만 그 지역에 이번 시즌 발견이 0건일 때
**똑같이 빈 응답**을 준다. 두 상태를 화면이 구분해야 하는 이유는 **①은 사용자가
할 일이 있고 ②는 없다**는 것이다. ①에서 "아직 이웃이 적어요"라고 말하면
**할 일이 있는 사람에게 기다리라고 하는 것**이 된다.

| 상태 | 문구 | 버튼 |
|---|---|---|
| 불러오는 중 | (기존 로딩 표시만 · 문구 없음) | — |
| 지역 미설정 | 활동 지역을 정하면 순위를 볼 수 있어요 / 같은 동네 이웃들과 꽃 수집 순위를 겨루게 됩니다. | `동네 선택하기` (Primary) |
| 이웃 발견 0건 | 아직 이 동네에 모은 꽃이 없어요 / 첫 번째로 남겨보세요 | `꽃 찍어보기` (Primary) |
| 조회 실패 | 연결이 불안정해요. 잠시 후 다시 시도해 주세요. | `다시 시도` (Secondary) |

- `지역 미설정`의 설명은 **화면 02의 `설명 1`을 그대로 쓴다** — 같은 것을 설명하는
  두 화면이 다른 말을 하면 사용자가 다른 기능으로 읽는다.
- `이웃 발견 0건`은 3절 빈 상태의 `지도에 기록 없음`(`아직 이 근처에 공유된 꽃이
  없어요 / 첫 번째로 남겨보세요`)과 **같은 구조**로 맞췄다. 지도와 랭킹이 같은
  "아무도 아직 안 했다"를 다른 말투로 말할 이유가 없다.
- `조회 실패`는 3절 토스트의 네트워크 오류 문구를 재사용한다. **새 문장을 만들지 않았다.**
- ⚠️ **`아직 이웃이 적어요`(2절 02번)를 여기 쓰지 않았다.** 그건 이웃 10명 미만일 때
  화면 02의 목록 항목에 붙는 라벨이고, 화면 17에서 이웃이 적다는 것은 **B-6 규칙이
  구 단위로 넓혀서 이미 해결한 상태**다(그때는 랭킹이 정상적으로 나온다).
  같은 문구를 다른 뜻으로 쓰면 둘 중 하나가 반드시 틀린 말이 된다.
- 🔴 **범위가 구로 넓어졌을 때(`scope = gu`) 제목을 `{동명}`으로 두면 거짓말이 된다.**
  서버가 `scope`를 돌려주는 이유가 그것이다(0002 SQL 2절 주석). 이 경우의 문구는
  **오너·디자이너 확인이 필요하다** — 아래 4절 7번에 올렸다.

### 친구 수를 모를 때의 문구 (2026-08-08 추가 · AOS 세션)

**왜 추가했나.** 2절 18·19·20에 친구 수가 세 번 나오는데 **전부 숫자가 박힌
문장**이다(`친구 8명과 겨루는 중` · `내 친구 {n}` · `친구 관리 8명`).
친구 수는 서버에 물어야 알 수 있고, **못 물어보는 경우가 있다**(연결 실패 ·
불러오는 중 · 서버 기능이 꺼진 빌드). 그때 쓸 문장이 없어서 추가했다.
**오너 검토 대상이다.**

| 화면 | 아는 경우 (기존) | 모르는 경우 (추가) |
|---|---|---|
| 18 제목 | 친구 8명과 겨루는 중 | 친구와 겨루는 중 |
| 19 탭 | 내 친구 8 | 내 친구 |
| 20 메뉴 | 친구 관리 `8명` | 친구 관리 (값 칸을 비운다) |

- 🔴 **모를 때 `0명`을 쓰지 않는다.** `친구 0명과 겨루는 중`은 **틀린 말**이고,
  게다가 0명은 화면 18에서 초대 화면으로 전환되는 조건이라 **친구가 있는 사용자에게
  `초대 링크 보내기`를 내민다**. 이미 친구인 사람을 다시 초대하라는 화면이 된다.
- 🔴 **모를 때 랭킹에 뜬 친구 수로 대신하지 않는다.** 서버 친구 랭킹은 **이번 시즌
  발견이 0건인 친구를 아예 안 준다**(실측). 그 숫자를 쓰면 화면 18이 `친구 3명`,
  화면 20이 `친구 관리 8명`이 되어 **같은 것을 두 숫자로 말한다.** (18)에서
  실제로 7 vs 8이 났던 자리다.
- 문장 구조를 바꾸지 않고 **숫자만 빼는 방식**으로 골랐다. 새 문장을 만들면
  "친구 기능에 문제가 생겼다"로 읽히는데, 사실은 숫자 하나를 못 받은 것뿐이다.

### 화면 20·21에서 **값이 없는 칸** (2026-08-08 추가 · AOS 세션)

**왜 추가했나.** 2절 20·21번 표는 값이 **항상 있는 화면**만 적혀 있다

시즌 종료 후 **본인이 안 눌러도 강제로 뜨는 전면 화면**이라(주석 ①) 값이 없을 때
무엇을 쓸지 정해 두지 않으면 그 화면이 거짓말을 한다. **오너 검토 대상이다.**

| 칸 | 아는 경우 (기존) | 값이 없을 때 |

- 🔴 **대표 칭호·배지에 예시 값을 남기지 않았다.** `우리 동네 꽃박사`는 1위 칭호이고

  아무 것도 안 해도 뜬다 — 한 번도 랭킹에 든 적 없는 사용자가 `연남동 4위`를 본다.

**두 문구가 같은 숫자 하나에 걸려 있는데, 그 숫자를 못 받는 경우가 있다** —
검색 결과가 한 화면에 여럿이라 동네마다 따로 물어야 하고, 그중 일부만 실패할 수 있다.
그때 쓸 문장이 없었다. **오너 검토 대상이다.**

| 상태 | 문구 |
|---|---|
| 이웃 10명 이상 (기존) | 이웃 1,284명 활동 중 |
| 이웃 10명 미만 (기존) | 아직 이웃이 적어요 |
| **모르는 경우 (추가)** | **(줄을 그리지 않는다 — 동네 이름만 남는다)** |

- 🔴 **모를 때 `0명`이나 `아직 이웃이 적어요`를 쓰지 않는다.** 두 문구 모두
  **"세어 봤다"는 뜻**이다. 못 세었을 때 쓰면 이웃이 1,284명인 동네를 **비어 있다고
  말하는 것**이고, 화면은 완벽하게 정상으로 보인다. 사용자는 그걸 보고 **6개월간

  숫자를 모를 때는 문장을 만들지 않고 **뺀다.**
- ⚠️ **줄을 빼도 동네는 고를 수 있다.** 이 줄은 참고 정보이고, 막아 세우면
  이웃 수 조회 실패가 **동네 선택 자체를 막는다.**

**🔴 이 숫자의 정의는 화면 17과 같아야 한다 — 서버에서 한 번만 센다.**

실측: `public_profiles`는 anon 키로도 `dong_code`별 개수를 준다(`206` ·
`Content-Range: 0-0/11`)므로 앱에서 바로 셀 수 있었다. **그런데 그건 가입자 수다.**
화면 17의 `{동명} 이웃 1,284명`은 서버 `region_ranking`의 `member_count`이고
**"이번 시즌 발견이 있는 사람" 수**다(0002 주석: "가입만 한 사람을 세면 10명을
넘겨도 랭킹이 텅 빈다"). 섞으면 화면 02에서 `이웃 12명`을 보고 고른 사용자가
화면 17에서 `이웃 3명`을 본다 — 위 친구 수 **7 vs 8과 똑같은 사고**다.
그래서 서버에 `dong_member_count`를 두고(0004) `region_ranking`과 **같은 집합**을 센다.
`아직 이웃이 적어요`의 기준 10명도 B-6의 최소 인원과 같은 값이다.

### 화면 03에서 **권한 카드가 두 장일 때의 제목** (2026-08-09 추가 · AOS 세션)

**왜 추가했나.** 2절 03번 제목이 `이 세 가지만 허용하면 준비 끝!`인데 **숫자가
문장에 박혀 있다.** 예선 빌드는 연락처 매칭을 넣지 않아 카드가 **두 장**이고,
그러면 제목이 **화면에 없는 세 번째 카드를 세고 있다.** 실측(에뮬레이터 온보딩 2/2)에서
카드는 2장인데 제목은 `세 가지`였다. **오너·디자이너 검토 대상이다.**

| 카드 수 | 제목 |
|---|---|
| 3장 (연락처 포함 · 기존) | 이 세 가지만 허용하면 준비 끝! |
| **2장 (예선 · 추가)** | **이 두 가지만 허용하면 준비 끝!** |

- 🔴 **숫자를 뺀 문장(`이것만 허용하면 준비 끝!`)으로 바꾸지 않았다.** `세 가지`는
  "몇 개만 하면 된다"를 **적게 느끼게 하는 장치**다(카드 3장이 한 화면에 다 보이는
  이유가 그것이다). 숫자를 빼면 몇 개인지 몰라 **끝이 안 보이는 절차**로 읽힌다.
- ⚠️ **이 줄은 위 `친구 수를 모를 때`와 판단이 다르다.** 거기서는 숫자를 **모르는
  것**이라 문장에서 뺐다. 여기서는 숫자를 **정확히 아는 것**(내가 그리는 카드 수)이라
  세어서 쓴다. 🔴 **모르는 값은 빼고, 아는 값은 센다** — 섞으면 둘 중 하나가 틀린다.
- ⚠️ 연락처를 되살리면 제목도 `세 가지`로 함께 돌아간다. 코드에서 **카드 수로
  고르게** 해 두었으므로(`PermissionIntroItem.all.size`) 따로 고칠 곳은 없다.

### 화면 14에서 **지도를 못 띄울 때** (2026-08-09 추가 · AOS 세션)

**왜 추가했나.** 2절 14번 표는 **지도가 나오는 화면**만 적혀 있다(검색창 · 필터 칩 ·
프리뷰 카드 · 길찾기). 그런데 카카오맵은 **타일 인증에 실패해도 예외를 던지지 않고**
회색 사각형만 남긴다. 그때 쓸 문장이 없어서 코드에 임시 문구(`지도를 불러올 수 없어요`)를
넣었다가 **A 문서에 없는 문구가 화면에 떠 있는 상태**가 됐다. 그래서 정식으로 올린다.
**오너·디자이너 검토 대상이다.**

| 상태 | 문구 | 버튼 |
|---|---|---|
| 불러오는 중 | (지도 배경만 · 문구 없음) | — |
| 내 기록 0건 | 아직 이 근처에 공유된 꽃이 없어요 / 첫 번째로 남겨보세요 (3절 `지도에 기록 없음` 재사용) | `꽃 찍어보기` (Primary) |
| **지도 인증·연결 실패** | 연결이 불안정해요. 잠시 후 다시 시도해 주세요. / 도감과 촬영은 그대로 쓸 수 있어요 | `다시 시도` (Secondary) |
| **지도 키가 없는 빌드** | (지도 탭을 그리지 않는다 — 문구도 버튼도 없다) | — |

- 🔴 **회색 지도를 그대로 두지 않는다.** 회색 사각형은 **"이 동네에 기록이 없다"로
  읽힌다.** 사용자는 꽃을 찍어도 지도에 안 나온다고 생각하고, 원인은 앱 밖(연결·콘솔
  설정)인데 **앱이 고장난 것으로 읽는다.** 위 `20 지표 3칸`을 `0종`으로 그리지 않는
  것과 같은 판단이다 — **값이 없는 것을 0으로 그리지 않는다.**
- 🔴 **`조회 실패`는 3절 토스트의 네트워크 오류 문구를 재사용한다.** 화면 17이 이미
  같은 문장을 쓴다(위 표). **새 문장을 만들지 않았다** — `지도를 불러올 수 없어요`는
  같은 상황을 다른 말로 말하는 것이고, 게다가 **"지도만 영구히 고장났다"로 읽힌다.**
  실제로는 잠깐 연결이 끊긴 것이라 **다시 누르면 된다.**
- 🔴 **`다시 시도` 버튼이 반드시 있어야 한다.** 실측(2026-08-09)에서 에뮬레이터 DNS가
  3초간 죽어 `MapAuthException(401)`이 났는데, 그 뒤 연결이 돌아와도 **화면이 오류
  상태에 갇혀 있었다** — 앱을 완전히 죽여야 지도가 다시 나왔다. 지하철·엘리베이터에서
  지도를 여는 것이 그 조건이다. 문구만 바꾸고 버튼을 안 주면 **말은 "잠시 후 다시"인데
  다시 할 방법이 없는 화면**이 된다.
- ⚠️ **두 번째 줄(`도감과 촬영은 그대로 쓸 수 있어요`)을 뺴지 않는다.** 지도가 안 되는
  것이 **앱 전체가 죽은 것으로 읽히면** 사용자가 촬영도 안 해 본다. 이 줄은 위
  `권한 재요청 시트`의 위치 문구(`도감 등록은 그대로 할 수 있어요`)와 **같은 구조**다.
- ⚠️ **키 없는 빌드에서는 문구를 띄우지 않는다.** 화면 17의 `NotConfigured`와 같은
  판단이다 — 눌러도 안 되고 **사용자 탓이 아니다.** 오류처럼 보이게 하면 안 된다.

### 화면 16에서 **값이 없거나 실패한 칸** (2026-08-11 추가 · AOS 세션)

**왜 추가했나.** 2절 16번 표는 값이 **항상 있는 화면**만 적혀 있다(`좋아요 12 ·
댓글 3` · `꽃보다효산 / 연남동 · 2시간 전`). 반응 데이터 층(`ReactionService`)을
만들면서 **표가 안 적은 칸이 네 개** 드러났다. 화면 20·21 때와 같은 종류의 구멍이다.
**오너 검토 대상이다.**

| 칸 | 아는 경우 (기존) | 값이 없을 때 (추가) |
|---|---|---|
| 반응 줄 | 좋아요 `12` · 댓글 `3` | (숫자를 못 받으면 **줄 전체를 뺀다**) |
| 댓글 작성자 이름 | 꽃보다효산 | 탈퇴한 사용자예요 |
| 댓글 목록 | 댓글 3줄 | 첫 댓글을 남겨보세요 (0건일 때) / `연결이 불안정해요…` + `다시 시도` (실패) |
| 작성자 지역 | 연남동 | 있는 것만 쓴다 (`2시간 전`만), 둘 다 없으면 줄을 뺀다 |

- 🔴 **못 받은 반응 수를 `좋아요 0 · 댓글 0`으로 그리지 않는다.** 화면 17의
  `이웃 수를 모를 때`와 같은 이유인데 여기가 더 나쁘다: 서버 함수
  `discovery_reactions`는 **볼 권한이 없는 기록에도 오류가 아니라 0을 준다**
  (0007 4절 — 집계라서 호출자의 RLS를 그대로 탄다). 즉 `0`은 "아무도 안 눌렀다"와

### 화면 16 **댓글 삭제** (2026-08-12 추가 · AOS 세션)

**왜 추가했나.** 2절 16번 표에 **댓글을 지우는 수단이 없다.** 그런데 C-9는 오너가
확정한 규칙이고(`댓글은 수정 불가 · 삭제는 본인과 사진 소유자`) 서버에도 그 자물쇠가
붙어 있다(0007 정책 → 0009 RPC). 즉 **규칙은 있고 문구만 없는 상태**였다.
3절 `확인 다이얼로그`에 있는 것은 `기록 삭제`(발견 기록)뿐이고, **댓글과 다른 것이다** —
기록 삭제는 자기 도감에서 사진까지 지우는 일이고 댓글 삭제는 남의 기록에 쓴 한 줄이다.
같은 문구를 재사용하면 `이 발견 기록을 지울까요?`가 댓글에 뜬다. **오너 검토 대상이다.**

| 칸 | 문구 |
|---|---|
| 댓글 우측 버튼 | 삭제 |
| 확인 다이얼로그 제목 | 이 댓글을 지울까요? |
| 확인 다이얼로그 본문 | 지우면 되돌릴 수 없어요 |
| 확인 다이얼로그 버튼 | 지우기 / 취소 |
| 삭제 성공 | 댓글을 지웠어요 |
| 삭제 실패 | 댓글을 지우지 못했어요 |

⚠️ **위 다이얼로그를 `기록 삭제`처럼 한 칸에 몰아 쓰지 않았다.** 3절 `확인 다이얼로그`의
줄은 `이 발견 기록을 지울까요? / 지우면 되돌릴 수 없어요 (\`지우기\` / \`취소\`)`처럼 한
칸에 넷이 들어 있는데, 그 모양이면 **`CopySourceTest`가 본문 문구를 승인하지 못한다** —
그 검사는 셀을 `/`로 쪼개므로 조각이 `지우면 되돌릴 수 없어요 (\`지우기\``가 되어
어느 규칙으로도 `지우면 되돌릴 수 없어요`만 꺼낼 수 없다(그 검사 주석의 ①과 같은
글자 모양 문제다). 즉 **한 칸에 몰아 쓰면 화면이 그 문구를 그려도 검사가 조용히
통과한다.** 내용은 `기록 삭제`와 같은 구조이고 칸만 넷으로 나눴다.

- 🔴 **`삭제`는 텍스트다. 휴지통 아이콘만 두지 않는다**(1절 44번). 댓글 한 줄 옆이라
  자리가 좁아서 아이콘으로 만들기 쉬운 자리인데, 이 규칙의 예외를 두지 않는다.
- 🔴 **버튼은 지울 수 있는 댓글에만 뜬다.** C-9의 두 갈래(내 댓글 · 내 사진의 기록에
  달린 댓글)에만 그린다. 전부 그려 두고 누를 때 막으면 **누를 수 있는데 실패하는
  버튼**이 되고, 그건 이 저장소가 이미 세 번 만든 `죽은 버튼`이다.
  ⚠️ 판정은 화면이 하지만 **자물쇠는 서버**다(`delete_comment` 본문). 화면 판정이
  틀려도 남의 댓글은 안 지워진다 — 반대로 화면 판정만 믿으면 안 된다는 뜻이기도 하다.
- 🔴 **`댓글을 지우지 못했어요`가 `연결이 불안정해요…`와 다른 이유.** 서버 RPC는
  **실패도 HTTP 200**으로 오고 본문 `false`만이 실패를 말한다(0009). 그 `false`는
  권한 없음·없는 id·미로그인을 **일부러 구분해 주지 않는다**(남의 댓글이 존재하는지
  알려 주지 않으려는 설계다 · 공유계약 `0009 승격`). 즉 다시 시도해도 결과가 같은
  경우가 섞여 있어서, `잠시 후 다시 시도해 주세요`는 **틀린 안내가 된다**
  (화면 01 `manual_linking_disabled`에서 같은 판단을 했다).
  ⚠️ 네트워크가 실제로 끊긴 경우(HTTP 0·5xx)는 그대로 `연결이 불안정해요…`다 —
  두 문구를 갈라 쓴다.
- 🔴 **`댓글을 지웠어요`를 낙관적으로 먼저 띄우지 않는다.** 서버가 `false`를 줄 수
  있으므로, 지워진 줄을 먼저 없애면 **안 지워진 댓글이 화면에서 사라진다**(다음에
  열면 되돌아 있다). 응답을 받고 목록을 다시 읽는다.
- ⚠️ **네 문구 전부 개발이 지어낸 말투다**(규칙 위반이므로 여기 적는다). 3절 빈
  상태의 `…예요` 어투와 `기록 삭제` 다이얼로그의 구조(`지울까요? / 되돌릴 수 없어요`)를
  그대로 따랐다. **오너·톤 검토에서 바뀔 수 있다**(4절 14번).

#### ⑥ 04 `전체 보기` · 20 `내가 공유한 꽃`이 여는 목록

| 칸 | 문구 |
|---|---|
| 헤더 (`전체 보기`로 들어올 때) | 발견 기록 |
| 헤더 (`내가 공유한 꽃`으로 들어올 때) | 내가 공유한 꽃 |

- ⚠️ **한 화면을 두 제목으로 연다.** 목록은 같은 기기 기록이고 `내가 공유한 꽃`만
  공개 범위로 걸러진다 — 제목이 같으면 걸러진 목록을 전체로 읽는다.
- 🔴 **`아직 모은 꽃이 없어요`(화면 22)를 재사용하지 않는다.** 공유가 0건인 것과

  그래도 **빈 화면으로 두지 않고 화면 22의 `아직 모은 꽃이 없어요`를 그대로 쓴다** —
  그 갈래에서는 목록이 빈 것이 곧 도감이 빈 것이라 그 문구가 참이고, 도달할 수 없다고
  적어 둔 자리에 실제로 도달하는 일이 이 저장소에서 있었다. 위 🔴은 **`내가 공유한 꽃`
  쪽에서 그 문구를 쓰지 말라는 것**이다(그쪽은 참이 아니다).

#### ⑦ 문구가 하나도 안 생긴 자리 — 17 `더 보기`

**새 문구가 없다.** 2절 17번의 `6위부터 더 보기`를 그대로 쓴다. 그래도 여기 적는
이유는 **이 버튼이 왜 죽어 있었는지가 기록과 달랐기** 때문이다.

- 🔴 **`서버 함수에 offset이 없어서`가 아니었다.** `region_ranking`은 동네 전체를
  한 번에 준다 — `order by` 뒤에 자르는 절이 아예 없다(0002). 즉 **더 보여줄 줄이
  이미 손에 있었고**, 없던 것은 offset이 아니라 `펼쳤나`를 담을 값 하나였다.
  `구현현황_AOS.md` §9의 `offset 없음` 메모는 사실이 아니었다.
- 🔴 **더 보여줄 줄이 없으면 버튼을 그리지 않는다.** 이웃이 3명인 동네에서
  `4위부터 더 보기`가 뜨면 **없는 순위를 가리키는 버튼**이고, 눌러도 목록이 안 늘어난다.
- 🔴 **숫자를 `마지막 줄 순위 + 1`로 세지 않는다.** 공동 4위가 둘이면 다음은 6위라
  `5위부터 더 보기`가 **존재하지 않는 순위**를 말한다. **숨은 첫 줄의 순위**를 그대로
  쓴다 — 목록이 실제로 이어지는 자리다(공동 순위가 걸쳐 있으면 이미 보인 숫자가
  다시 나오는데, 그 순위에 못 보여준 사람이 남아 있으므로 참이다).
- ⚠️ **`5줄`은 우리가 정한 값이다**(`RankingRules.VISIBLE_ROWS`). 이걸 바꾸면
  2절 17번의 예시 문구 `6위부터`도 같이 틀린다.

### 로그인 없이 쓸 수 있는 범위 — **판별 2회** (2026-08-14 추가 · AOS 세션)

**오너 결정(2026-08-14).** `들어와서 보는건 비로그인 가능, 액션하려면 로그인 필요` ·
`도감등록 - 비로그인은 판별 디바이스당 2회` · `여기 판별은 성공이라고 하면 될듯하다`.

🔴 **2절 01번 표와 구조가 다르다.** 2절 01번은 로그인 3버튼만 있는 **전면 게이트**이고,
이 결정은 **비로그인으로 앱에 들어와서 2회까지 써 보는** 구조다. 즉 화면 01은
첫 실행에 뜨지 않는다 — 3회째 촬영에서 **시트**로 뜬다. 와이어프레임 01의 자리가
바뀌는 것이라 **디자이너 확인이 필요하다**(4절 19번).

| 칸 | 문구 |
|---|---|
| 로그인 요구 시트 제목 | 로그인하시고 더 많은 꽃을 만나보세요 |
| 로그인 요구 시트 확인 버튼 | 카카오로 3초 만에 시작하기 |
| 로그인 요구 시트 취소 버튼 | 나중에 할게요 |

- 🔴 **`로그인 하시고`가 아니라 `로그인하시고`다.** `로그인하다`는 한 단어라 붙여 쓴다.
  오너가 준 원문은 띄어 있었고 **맞춤법만 고쳤다** — 40~50대 대상이라 표기가 스펙의
  일부다(0절). 뜻은 한 글자도 바꾸지 않았다.
- 🔴 **확인·취소 버튼은 새 문구가 아니다.** 2절 01번의 `카카오로 3초 만에 시작하기`와
  1절 Ghost 예시의 `나중에 할게요`를 **그대로 재사용**한다. 시트 전용 버튼 문구를
  지어내지 않는다.
- ⚠️ **`3초 만에`는 참이 아닐 수 있다.** 이 앱의 카카오 로그인은 **웹 OAuth**라
  브라우저가 열리고 카카오 계정을 입력한다 — 카카오톡 앱으로 넘어가는 간편로그인이
  아니다(`KakaoLogin` 주석). 문구를 재사용한 것은 새로 지어내지 않기 위한 것이고,
  **톤 검토 대상이다**(4절 20번).
- 🔴 **설명 줄을 만들지 않았다.** 제목만으로는 `왜 지금 막혔는지`가 화면에 안 적힌다 —
  1절 `Disabled` 규칙(`왜 못 누르는지 쓴다`)과 어긋나는 자리다. 그런데 그 문장은
  오너가 준 것이 없어서 **지어내지 않았다**(4절 19번에 올렸다).
- ⚠️ **`지금은 로그인 없이 바로 쓸 수 있어요`(위 `화면 01에서 로그인 버튼을 누를 수
  없을 때`)를 여기 돌려쓰지 않는다.** 그 문구는 **제한이 없다는 뜻**이라 2회 제한이
  붙은 뒤에는 **거짓**이다. 그 표는 서버가 다시 꺼질 때를 위해 그대로 남긴다.

#### 무엇이 막히고 무엇이 안 막히나

| 행위 | 비로그인 | 왜 |
|---|---|---|
| 도감·지도·랭킹·남의 기록 **열람** | ✅ 제한 없음 | 오너 결정 `들어와서 보는건 비로그인 가능` |
| 촬영 → 판별 → **도감 등록** → 지도 공유 | **판별 성공 2회까지** | `더 많은 꽃을 만나보세요`가 이미 모은 것을 전제한다 |
| **댓글 쓰기 · 좋아요 · 신고** | ❌ 0회 | 남의 기록에 관여하는 행위다. 신고는 처리 대상을 특정해야 하고, 댓글은 UGC라 **책임 주체가 있어야** 한다 |

- 🔴 **위 표의 `댓글 쓰기`를 `댓글`로 줄이지 않는다.** 이 표는 **정책 표**인데
  `CopySourceTest`는 **모든 표 셀을 승인 문구로 읽는다** — ` · `로 쪼개고 굵게를 벗기면
  `댓글`이 승인 문구가 된다. 그 `댓글`은 2026-08-12에 **코드에서 지운 섹션 제목**이고
  (3절 마지막 표에 취소선으로 남아 있다), 승인되는 순간 지어낸 제목이 되살아난다.
  실제로 이 줄을 처음 `**댓글 · 좋아요 · 신고**`로 쓰자 그 검사가 빨개졌다 —
  **문서 한 줄이 검사를 껐다.** 같은 사고를 이걸로 네 번째 막았다.
- 🔴 **`내 기록을 만드는 것`과 `남의 것에 관여하는 것`으로 갈랐다.** 공유(화면 13)는
  등록 흐름의 마지막 단계라 2회 안에 넣었다 — 여기서 끊으면 **등록은 됐는데 공유
  화면에서 막히는** 흐름이 된다.
- ⚠️ **소급 적용하지 않는다.** 이미 비로그인으로 3종 이상 모은 기기의 도감을 잠그면
  **쓰던 사람의 기록이 잠긴다.** 제한은 `앞으로의 판별`에만 걸린다.

#### 🔴 `판별 성공`의 정의 — 여기를 틀리면 화면에 증상이 없다

| 경우 | 세나 | 왜 |
|---|---|---|
| 후보가 1개 이상 화면에 떴다 (화면 09 · 09변형) | ✅ 센다 | 체험을 했고 API 호출도 썼다. `이 꽃이에요`를 **안 눌러도** 센다 |
| 후보가 전부 `MIN_CONFIDENCE_FOR_ANY_CANDIDATE` 미달 (화면 12) | ❌ | 사용자에게는 실패다. 이걸 세면 **2회를 못 써 보고 막힌다** |
| 네트워크 실패 · 타임아웃 · API 일일 한도 초과 | ❌ | 우리 잘못을 사용자 몫으로 세는 것이 된다 |

⚠️ **어느 쪽으로 틀려도 화면에는 아무 증상이 없다.** 많이 세면 2회를 못 써 보고
막히고, 적게 세면 무한히 쓴다 — 둘 다 정상 화면이다. 그래서 판정을 화면의 `if`가
아니라 `LoginGate`에 두고 검사로 고정한다.

#### 🔴 `디바이스당`은 지킬 수 없다 — 그렇게 적는다

앱을 지우고 다시 깔면 카운터가 **0으로 돌아간다.** 진짜 기기 단위로 묶으려면
`ANDROID_ID` 같은 **하드웨어 식별자**가 필요한데, 그건 Play 정책·개인정보처리방침
쪽에서 더 큰 문제를 만든다 — **쓰지 않는다.**

⚠️ 즉 이 제한은 **로그인 유도**로는 일하고, **어뷰징 차단**은 못 한다.
그리고 **API 쿼터 방어도 아니다** — 로그인한 사용자는 무제한이므로 사용자가 늘면
그대로 한도에 닿는다(`AI인식_API_비용검토.md`).

| 11 | **`나중에 하기` vs `나중에 할게요`** | 같은 뜻의 회피 버튼이 앱에 **두 문장**으로 있다 — 화면 02 헤더는 `나중에 하기`, 화면 12 Ghost는 `나중에 할게요`(1절 Ghost 예시도 후자). 중장년 타깃이라 종결 통일이 스펙의 일부인데 여기가 갈려 있다. **하나로 정해 주면 코드를 맞춘다** — 지금은 코드 현행을 3절에 적어 두었다(위 표) |
| 12 | **`이 꽃이에요` vs `이거예요`** | 화면 09에서 후보를 고르는 문구가 **한 화면 안에 두 문장**으로 있다 — 1순위 확실 화면의 후보 행은 `이 꽃이에요`, 임계값 미달 변형의 후보 행은 `이거예요`. 11번과 같은 종류이고, 여기는 **같은 화면**이라 더 눈에 띈다. 그리고 09번 표에 **후보 목록 자체가 없다**(B-3 ③으로 생긴 UI다) — 그 목록의 문구 전체를 확정해 주면 3절 표를 지운다 |
| 13 | **9개 문구의 톤 검토** | 3절 `코드에 있는데 표에 없던 버튼 아닌 문구 9개`가 전부 개발이 지어낸 말투다. `…예요`체는 맞췄지만 어휘·존대 수준을 검토받은 적이 없다. 특히 `가장 비슷한 꽃을 골라 주세요`는 **사용자에게 판별을 떠넘기는 말**로 읽힐 수 있다(AI가 못 했다는 뜻이 앞에 없다) |
| 14 | **화면 16 댓글 삭제 문구 4개** | 3절 `화면 16 댓글 삭제`(2026-08-12)의 네 문구가 개발이 지어낸 것이다. 특히 **`댓글을 지우지 못했어요`가 이유를 말하지 않는다** — 서버가 권한 없음·없는 id·미로그인을 일부러 구분해 주지 않기 때문이다(그게 설계다). 사용자는 "왜 안 지워지는지" 모르는 채 같은 버튼을 다시 누른다. 이유를 말하려면 **서버 응답을 갈라야 하고, 그러면 남의 댓글이 존재하는지가 노출된다** — 문구로 해결할 문제가 아니라 그 교환을 결정해야 한다. 그리고 `삭제` 버튼이 **댓글 한 줄 옆**이라 자리가 좁다(1절 44번 때문에 아이콘 단독은 안 된다) — 위치·크기 확인 필요 |
| 15 | **새 문구 24개의 톤 검토** (2026-08-13) | 3절 `죽은 버튼 14개를 실제 기능으로 바꾸며 생긴 문구`가 전부 개발이 지어낸 말투다. 13·14번과 같은 종류지만 **①의 세 줄은 성질이 다르다** — 공유 시트로 나가서 **다른 앱에 사용자 이름으로 붙는다.** 우리 화면에는 안 보이므로 검토에서 빠지기 쉽다. `캐치플라워에서 {꽃이름}을 모았어요`가 자랑으로 읽히는지, `같이 동네 꽃을 모아요`가 광고처럼 읽히지 않는지 확인 필요 |
