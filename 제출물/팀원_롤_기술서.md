**구체적으로 한 일**

- 게임 기획과 정책 **35항목**을 정수지와 함께 정하고, 그중 코드로 내려가는 값(개화월 하드 필터, 판별 실패 floor **0.05**, 랭킹 확장 규칙)을 **실측 근거를 붙여** 확정했다.
- Android 앱을 처음부터 끝까지 만들었다 — 화면 **22개 중 19개**가 동작하고, 촬영 → ML Kit 1차 필터 → 개화월 압축 → **PlantNet 실호출** → 도감·지도 등록까지 **실기기(Galaxy A25)** 에서 확인했다.
- iOS(SwiftUI)와 Supabase 백엔드(테이블 6 · enum 6 · RLS · 함수 5개)를 **같은 계약 문서 위에서** 병행했다 — 두 플랫폼이 같은 DB를 쓰므로 필드명·enum·정책값을 문서로 묶었다.
- 판별 정확도를 **측정으로** 잡았다 — PlantNet **200장**과 온디바이스 필터 **1,000장**을 채점해 실패 floor를 0.30 → 0.05로 내리고 **정답률 50% → 80%**로 올렸다.
- 테스트 **454개**(JVM 409 · 계측 45)와 **돌연변이 검증 182건**으로 "초록인데 틀린" 검사를 걸러 냈다. APK · GitHub Pages · 제출 문서 · 플레이 영상까지 배포도 담당했다.

- 문구·버튼 스펙(`A` 문서)을 함께 확정했다 — 문구가 한곳에 모여 있어서 **개발이 화면 문구를 새로 창작하지 않았다.**

## 4. 협업 방식

### 4-1. 형상 관리

| | |
|---|---|
| 저장소 | https://github.com/Aaron-HyoSan/catchflower (공개) |
| 브랜치 | `main` |
| 커밋 | **46개** (2026-08-04 ~ 08-10) |
| 커밋 규칙 | `[iOS]` / `[AOS]` / `[공용]` 접두 — 어느 플랫폼 변경인지 제목에서 보인다 |

### 4-2. iOS · Android 동시 개발을 어떻게 어긋나지 않게 했나

터미널(작업 세션) 2개를 병행했다. 같은 서버·같은 DB를 쓰므로 **한쪽이 필드명을 바꾸면
다른 쪽이 조용히 깨진다.** 그래서 문서 하나를 상위 규칙으로 뒀다.

| 문서 | 역할 |
|---|---|
| `공유계약_iOS_AOS.md` | DB 컬럼명 · enum 문자열 · 정책 숫자 · Mock 동작. **혼자 못 바꾼다** |
| `세션시작_iOS.md` / `세션시작_AOS.md` | 새 작업 세션이 **가장 먼저** 읽는다 (환경 · 금지사항) |
| `구현현황_iOS.md` / `구현현황_AOS.md` | 지금 무엇이 되고 **무엇이 안 되나** |
| `진행.md` | 스텝이 끝날 때마다 덧붙인다 — **무엇을 했는지가 아니라 무엇이 틀렸는지** |

실제로 한쪽이 `ai_confidence`를 Double로 넓혀 다른 쪽 파싱이 깨진 일이 있었고,
그 뒤로 **계약 문서를 고치고 기록한 다음에만 코드를 고치는** 순서로 굳혔다.

### 4-3. 의사 결정 기록

정책 **35항목**을 `오너_결정사항.md`에 모아 두고, 확정된 것만 코드에 반영했다.
예: 판별 실패 floor **0.05**는 실측 근거를 붙여 승인받은 값이고, iOS·Android 공용
계약값이라 **어느 한쪽이 혼자 바꿀 수 없다.**

### 4-4. 디자인과 개발을 어떻게 넘겼나

문구와 화면 요구를 **문서 원본 하나로** 고정했다 — `A_문구·버튼_스펙.md`(전 화면 문구)와
`B_화면_UI디자인_업무목록.md`(화면 22개 · 타깃 제약). 개발이 화면을 만들 때 문구를 새로
쓰지 않고 이 문서에서 가져오기 때문에, **문구를 고치면 앱이 따라온다**(반대 방향으로
흐르지 않는다). 일러스트 200장은 `C_꽃일러스트_발주서.md`의 규격(PNG 512×512 RGBA)에 맞춰
`꽃목록_200종.csv`의 도감 번호와 파일명으로 짝지었다 — 200장이 전부 512×512로 들어온 것을
파일 메타로 확인했다.

도감을 2,057종으로 넓히면서 **일러스트 500장을 프로그램으로 추가**했다. 이것은 정수지의
200장과 출처가 다르므로 폴더와 문서에서 갈라 뒀다(`AI_활용_기술문서.md` 6-1절). 프로그램은
**기존 200장을 실측한 값**을 목표로 삼는다 — 꽃 폭·꽃 상단 위치·잎 bbox·초록 화소 비율·
꽃/잎 면적비 5개 축. 🔴 그런데 **다섯 축이 다 맞아도 닮은 것이 아니었다**: 면적비가 0.55일 때
잎이 꽃보다 먼저 보였고, 크기·bbox 검사는 전부 통과한 상태였다. 나란히 놓고 봐야 보였다.
색은 원천 데이터에 없어 새로 만든 값이라(76%가 과 기본색) `_스펙.csv`에 근거 등급을 남겨
검수 대상을 지목해 뒀다.
