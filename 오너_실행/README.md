### 🔴 2026-08-11 정정 — 아래 두 가지가 이 문서에서 틀려 있었다

**① "지도 SDK가 아직 앱에 안 붙어 있다"는 틀렸다.** 지금은 붙어 있다 —
`com.kakao.maps.open:android:2.14.1` 의존성과 `ui/map/`(`MapScreen`·`MapViewModel`·

낡은 기대값을 보고 대조하면 **정상인데 ❌로 읽거나, 틀렸는데 ✅로 읽는다.**

🔴 **그리고 여기서 또 틀렸다(2026-08-12).** 이 자리에 `지금은 2,057종 · 함수 13개 ·
14줄이다`라고 **새 숫자를 다시 적었고, 그것도 낡았다**(그 뒤 0007·0008이 들어왔다).
낡은 숫자를 고치는 방법으로 **새 숫자를 적는 것**을
택한 게 잘못이었다 — 같은 실수를 한 자리에서 두 번 했다.

→ 그래서 이 문서에서는 **개수를 아예 적지 않는다.** 기대값은
`02_적용확인.sql`이 스스로 들고 있고, 돌리면 화면에 `실제 ⟵ 기대`로 같이 찍힌다.
`supabase/_tools/check_migrations.py`가 이 문서에 개수가 다시 새어 들어오면 잡는다.

⚠️ 키 해시는 **이 맥의 디버그 서명**에 딸린 값이다(아래 2절). 그래서
**출시용으로 서명한 APK는 지도가 조용히 안 뜬다** — 지금 전달하는 것은 디버그 APK다.

## 1. DB 스키마 적용 (Supabase) — ✅ **끝났다**

⚠️ **아래는 다시 할 일이 아니라 기록이다.** 이미 적용됐고, 표·정책·함수가 실제로
도는 것까지 확인했다. 다른 맥/새 프로젝트에서 처음부터 세울 때만 다시 본다.

**왜 내가 해야 하나.** 앱이 쓰는 `anon` 키에는 표를 만들 권한(DDL)이 없다.
일부러 그렇게 뒀다 — 앱이 표를 만들 수 있으면 **누구나 남의 표를 지울 수도 있다.**
표를 만드는 건 대시보드에 로그인한 사람만 할 수 있고, 그게 오너다.

### 순서

1. https://supabase.com/dashboard 접속 → 프로젝트 `ngfkkazyvbbhrcznqkar` 선택
2. 왼쪽 메뉴 맨 아래쯤 **`SQL Editor`** (아이콘이 `>_` 모양) 클릭
3. **`+ New query`** 클릭
4. 이 폴더의 **`01_스키마_전체.sql`** 파일을 열어 **전체 선택(⌘A) → 복사(⌘C)**
5. SQL Editor 창에 **붙여넣기(⌘V)**
6. 오른쪽 아래 **`Run`** 클릭 (또는 `⌘Enter`)
7. 기다린다. **꽃 2,057종을 넣기 때문에 파일이 크다**(약 380KB · 3,400줄) —
   붙여넣기와 실행에 각각 몇 초에서 몇십 초 걸릴 수 있다

⚠️ **붙여넣기가 느리거나 편집기가 잠깐 멈춰도 정상이다.** 파일의 대부분(약 280KB)이
   꽃 데이터 한 줄짜리 `insert`다. 브라우저가 버거우면 대신 이렇게 나눠도 된다 —
   **번호 순서만 지키면 결과는 같다**(`supabase/migrations/` 폴더의 원본 파일):

   `0001_init` → `0002_ranking` → `0003_seed_flowers` → `0004_region_change`
   → `0005_flowers_expand_2057` → `0006_seed_flowers_2057`

   🔴 **순서를 바꾸면 1,857종이 전부 거부된다.** `0005`가 도감 번호 상한을
   200 → 2,057로 넓히는 파일이라 `0006`보다 **먼저** 돌아야 한다.

### ⚠️ "Success. No rows returned"는 성공했다는 뜻이 **아니다**

**아무것도 만들지 않고 끝났을 때도 똑같은 메시지가 나온다.** 그래서 세어서 확인한다.

8. **`+ New query`** 로 새 창을 열고 **`02_적용확인.sql`** 을 똑같이 붙여넣고 `Run`
9. 표가 나오는데 **`판정` 칸이 19줄 전부 ✅ 여야 한다**

⚠️ **이 표를 여기 옮겨 적지 않는다.** 기대값의 원본은 `02_적용확인.sql` 한 곳이고,
   여기에 베껴 두면 **낡은 기대값을 보고 정상을 ❌로, 틀린 것을 ✅로 읽는다** —
   실제로 그 일이 두 번 났다(2026-08-11에 `표 6개·함수 13개·정책 17개`로 낡아
   있었고, 0007·0008이 들어오면서 각각 8·17·23으로 바뀌었다).
   **파일이 기대값을 스스로 들고 있고, 화면에 `실제 ⟵ 기대`로 같이 찍힌다.**
   → 그러니 여기서는 **줄 수와 ✅ 개수만** 본다.

| 무엇 | 값 |
|---|---|
| 나와야 하는 줄 수 | **19줄** (0001~0008) |
| `판정` 칸 | **전부 ✅** |
| 18·19번이 ❌면 | **0008을 아직 안 돌린 것**이다 → 3절 |

**하나라도 ❌ 가 있으면 그 줄을 그대로 캡처해서 보여주면 된다.**

### 🔴 4·12·13번이 왜 있나 — **"2,057종이 들어갔다"만으로는 부족하다**

이 세 줄은 **종수가 2,057로 맞는데도 조용히 망가진 상태**를 잡는다.

| # | 잡는 것 | 이게 뚫리면 |
|---|---|---|
| **4** | 확장 초안이 **사람이 정한 200종을 덮었는가** | 종수·화면 다 정상인데 **판별 Top-1이 77% → 50%**로 떨어진다 (실측). 튤립은 40장 중 **0장** 맞춘다 |
| **12** | 어떤 적재가 **개화기 근거를 안 적었는가** | "사람이 확인한 값"의 수가 부풀어 **채워야 할 목록이 줄어 보인다** |
| **13** | `1~12월에 피는 꽃` 문구가 나가는가 | "12개월 모두 관찰됐다"를 **"일 년 내내 핀다"고 단정**하는 문장이 된다 (상록수 9종) |

4번이 특히 중요하다 — **개화월이 판별의 하드 필터**라서, 초안이 실제 개화월을
빠뜨린 종은 **후보에 아예 안 오른다.** 앱은 멀쩡해 보이고 빌드도 테스트도 통과한다.

⚠️ **꽃 3줄만 나오면 그건 스키마 문제가 아니다.** 예전 `02_적용확인.sql`은 문장이
2개였고, **SQL Editor는 여러 문장을 돌리면 마지막 결과만 보여준다** — 앞의 확인 표가
조용히 가려졌다. 지금 파일은 문장이 하나라서 표가 바로 나온다.

### 실수해도 괜찮다

- **두 번 돌려도 안전하다.** 이미 있는 건 건너뛰고 데이터는 덮어쓰도록 썼다
  (`if not exists` · `create or replace` · `on conflict do update`)
- **중간에 빨간 에러가 나도 앞부분은 남는다.** 고친 뒤 그냥 다시 `Run` 하면 된다
- 붉은 글씨가 떠도 **그 메시지를 그대로 보여주면 된다.** 지우거나 되돌릴 필요 없다

### 이 SQL이 뭘 하나 (궁금하면)

⚠️ **개수를 여기 적지 않는다** — 아래 세 줄이 원래 `표 6개 · 접근정책 17개`였는데
   0007·0008이 들어오면서 **8개 · 23개**가 됐고, 아무도 안 고쳤다. 정확한 수는
   `02_적용확인.sql`을 돌리면 `실제 ⟵ 기대`로 같이 나온다.

- 도감·사용자·발견기록·친구·차단·신고, 그리고 좋아요·댓글 표
- 랭킹 함수: **랭킹을 서버가 센다.** 앱이 세면 숫자를 조작할 수 있다
- 접근정책: **남의 기록을 못 보게 하는 규칙.** 비공개 기록은 본인만,
  친구공개는 서로 수락한 친구만 보인다

### ⚠️ 2,057종을 등록한다는 것이 "2,057종을 다 안다"는 뜻은 아니다

솔직하게 적어 둔다. 신규 1,857종은 **채울 근거가 없는 칸이 있다.**

| 칸 | 비어 있는 종 | 화면에서 |
|---|---|---|
| 개화기 표기 | **1,026종** | `장미과 · 5~6월에 피는 꽃` → **`장미과`** (절을 뺀다) |
| 대표색 | 1,857종 | 속성 칩이 하나 줄어든다 |
| 주요서식지 | 1,857종 | 꽃 이야기에서 그 문장을 뺀다 |
| 일러스트 | 1,857종 | 그림 자리에 도감 실루엣이 나온다 |

**빈칸을 그럴듯한 말로 채우지 않았다.** 채우면 "모르는 것을 아는 것처럼"
말하게 되고, 개화월은 판별의 하드 필터라 **틀린 값이 그 종을 영구히 지운다.**
어떤 근거로 정했는지는 `bloom_source` 칸에 함께 저장해 뒀다 —
그래서 나중에 **사람이 채울 목록을 셀 수 있다**(12번 확인 줄이 그 수를 본다).

## 2. 카카오 키 해시 등록

**왜 내가 해야 하나.** 카카오 콘솔은 앱 소유자 계정으로 로그인해야 들어간다.

**키 해시란.** "이 앱이 정말 그 앱인가"를 카카오가 확인하는 지문이다.
등록 안 하면 지도를 불러도 **`잘못된 앱 키`** 로 거부된다.

### 등록할 값 (이 맥의 디버그 키 해시)

```
Vbb1YnBobsq+CLwfh3xnNgVs6a8=
```

끝의 `=` 까지 **그대로 복사**한다. 이건 비밀값이 아니라 공개해도 되는 지문이다.

### 순서

1. https://developers.kakao.com 로그인
2. 상단 **`내 애플리케이션`** → **네이티브 앱키가 `3bf6d46…65e` 로 시작/끝나는 앱** 선택
   - 앱이 여러 개면 각 앱의 `앱 키` 메뉴에서 네이티브 앱키 앞 7자리를 대조한다
   - (이 문서는 git에 올라가므로 **앱키 전체는 적지 않았다.** 전체 값은
     `android/local.properties`의 `KAKAO_NATIVE_APP_KEY` 에 있다 — 그 파일은 커밋되지 않는다)
3. 왼쪽 **`앱 설정` → `플랫폼`**
4. **`Android`** 쪽 **`수정`** (없으면 `Android 플랫폼 등록`)
5. 두 칸을 채운다:
   - **패키지명**: `com.catchflower.app`
   - **키 해시**: 위 `Vbb1YnBobsq+CLwfh3xnNgVs6a8=`
6. **`저장`**

### ⚠️ 이 키 해시는 **이 맥에서만** 통한다

키 해시는 **서명 키의 지문**이라 기기가 아니라 **빌드한 컴퓨터**에 딸린다.

| 상황 | 필요한 것 |
|---|---|
| 지금 이 맥에서 개발·테스트 | 위 값 하나로 끝 |
| 다른 맥에서 빌드 | 그 맥의 값을 **추가로** 등록 (여러 개 등록 가능) |
| 스토어 출시 | **출시용 키 해시를 따로 등록해야 한다.** 디버그 값으로는 출시 앱이 안 된다 |

출시할 때가 되면 그때 다시 계산해 드리겠다 — **지금 미리 할 필요는 없다.**

다른 맥에서 직접 뽑고 싶으면:

```
keytool -exportcert -alias androiddebugkey \
  -keystore ~/.android/debug.keystore \
  -storepass android -keypass android \
  | openssl sha1 -binary | openssl base64
```

## 3. 댓글 삭제 고침 — `supabase/migrations/0008_comment_delete_fix.sql`

**증상.** 앱에서 **자기가 쓴 댓글을 지우려 하면 거부된다**(`403 · 42501`).
좋아요는 지워진다. 댓글만 안 된다.

### 순서

1. Supabase → `SQL Editor` → `+ New query`
2. `supabase/migrations/0008_comment_delete_fix.sql` 전체 복사 → 붙여넣기 → `Run`
3. **마지막에 표가 8줄 나온다. 그 표를 그대로 캡처하거나 복사해서 보여준다**

### 🔴 3번이 이 작업의 절반이다 — 나는 **원인을 아직 모른다**

솔직하게 적는다. `0007` 파일 원문은 **바이트까지 정확**했다 — 정책이 제대로 쓰여
있다. 그런데 서버는 거부한다. 즉 **파일과 서버의 실제 상태가 다르다.**

⚠️ 앱이 쓰는 `anon` 키로는 `pg_policies`(정책 원문이 든 표)를 **읽을 수 없다.**
그래서 내가 원격으로 확인할 방법이 없다. 이 파일의 마지막 문장은 **서버가 자기
정책 원문을 스스로 말하게 하는 조회**다 — 그 8줄이 원인을 가른다.

⚠️ **로컬에 postgres가 없어서 이 파일의 트리거를 미리 태워 보지 못했다**(이 맥에
`psql`·`docker`가 없다). 문법 검사는 통과했지만 **그건 문법일 뿐이다.** 그래서
표의 마지막 줄이 "트리거가 붙었나"가 아니라 **"트리거 본문이 네 칸을 다 막나"** 를
원문에서 센다 — 붙었는데 아무것도 안 막는 상태가 가능하다.

**빨간 에러가 나도 그 메시지를 그대로 주면 된다.** 되돌릴 필요 없다.

## 4. 카카오 로그인 — 콘솔 **4곳** (앱이 켤 수 없다)

앱 쪽 코드는 만들어 뒀다. **서버 설정 2개가 꺼져 있어서 버튼을 일부러 못 누르게
막아 놨다.** 아래를 켜면 내가 다시 재고 버튼을 연다.

| # | 어디 | 무엇을 | 이게 없으면 |
|---|---|---|---|
| ① | developers.kakao.com → 내 애플리케이션 → **카카오 로그인** | **활성화 ON** + 동의항목에서 `닉네임(profile_nickname)` **필수 동의** | 닉네임이 안 와서 **랭킹에 이름이 빈다** |
| ② | 같은 화면 → **Redirect URI** | `https://ngfkkazyvbbhrcznqkar.supabase.co/auth/v1/callback` 추가 | 카카오가 인증 후 **돌아올 곳을 모른다** |
| ③ | Supabase → `Authentication` → `Sign In / Providers` → **Kakao** | **Enable** + `REST API 키` + `Client Secret` | `provider_disabled` — 버튼을 눌러도 거부된다 |
| ④ | 같은 화면 아래 → **Manual Linking** | **Enable** | 🔴 아래를 반드시 읽는다 |

### 🔴 ④를 빼고 ①~③만 켜면 **기록이 사라진다**

지금 모든 사용자는 **익명 계정**이고, 도감·업로드·랭킹이 그 계정 번호에 묶여 있다.
`Manual Linking`은 **"기존 익명 계정에 카카오를 붙인다"** 는 기능이다. 이게 꺼져
있으면 카카오 로그인이 **번호가 다른 새 계정**을 만들고, 그 순간 그때까지의 서버
기록은 **보이지도, 지우지도 못하는 데이터**가 된다(접근 규칙이 계정 번호로 걸려 있다).

⚠️ **그런데 화면에는 도감이 그대로 보인다** — 사진이 폰 안에 있으니까. 오류도 안 뜬다.
없어지는 건 업로드와 랭킹뿐이고, 그건 **한참 뒤에나 눈에 띈다.**

실측으로 확인한 것이다 — 익명 계정으로 연결을 태워 보니 카카오·구글·**없는
provider까지 셋 다 똑같이** `manual_linking_disabled`를 준다. provider 문제가 아니라
**기능 자체가 꺼져 있다.**

### 🔴 `Client Secret`은 **Supabase 콘솔에만** 붙여넣는다

**나에게 보내지 말라.** 코드에도 안 넣는다. ③번 칸에 직접 붙여넣으면 끝이고,
나는 그 값을 알 필요가 없다.

### 켠 뒤에 알려주면 된다 — **값만 바꾸면 안 된다**

⚠️ Supabase는 이 기능이 켜졌는지를 **조회로 알려주지 않는다**(확인해 봤다. 설정
응답에 그 항목이 없다). 실제로 한 번 태워 봐야만 안다. 그래서 **"켰다"는 말만 듣고
앱 상수를 바꾸지 않는다** — 익명 계정으로 다시 재고 나서 버튼을 연다.

### 지금 화면 01(로그인 화면)이 없는 이유

버튼 3개(카카오·애플·휴대폰)가 **전부 눌릴 수 없는 상태**다. 만들면 죽은 버튼만
있는 화면이 된다. **로그인 없이도 앱 전체가 동작하니까**(익명 계정) 급하지 않다.
문구는 `디자이너_업무/A_문구·버튼_스펙.md` 3절에 미리 적어 뒀다.
